1. Why SQL Is Essential in Software Testing

A green UI message like "Order Placed Successfully" only proves the frontend rendered a banner—not that the backend persisted the right totals, tax calculations, or inventory deductions. QA engineers use SQL to:

  • Verify Data Persistence: Confirm UI and REST API actions write accurate rows and timestamps to the database.
  • Prepare & Clean Up Test Data: Query valid test accounts (e.g., active users with zero pending orders) or reset test state cleanly.
  • Validate Data Integrity & Migrations: Catch duplicate records, orphaned foreign keys, null violations, and ETL transformation bugs.

3. Core Querying: Filtering, Sorting & Null Checks

Notice the logical execution order of a SQL query: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY.

-- 1. Filter completed high-value orders and sort newest first
SELECT order_id, customer_id, total_amount, order_date
FROM orders
WHERE order_status = 'COMPLETED'
  AND total_amount >= 100.00
ORDER BY order_date DESC;

-- 2. Pattern matching with LIKE and membership with IN
SELECT customer_id, full_name, email
FROM customers
WHERE account_tier IN ('Premium', 'Enterprise')
  AND email LIKE '%@example.com';

-- 3. Checking for missing/NULL values (never use '= NULL')
SELECT order_id
FROM orders
WHERE order_status IS NULL;

4. Combining Tables with JOINs (INNER vs. LEFT JOIN)

Normalized databases split entities across multiple tables. Understanding INNER JOIN vs. LEFT JOIN is critical for finding missing records:

-- INNER JOIN: Returns only customers who have placed at least one order
SELECT c.full_name, c.account_tier, o.order_id, o.order_status, o.total_amount
FROM customers c
INNER JOIN orders o ON c.customer_id = o.customer_id;

-- LEFT JOIN: Keeps ALL customers (even those with zero orders — Diya Krishnan)
-- QA Pattern: Find customers who have NEVER placed an order (o.order_id IS NULL)
SELECT c.customer_id, c.full_name, c.email
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
WHERE o.order_id IS NULL;

5. Aggregations, GROUP BY, HAVING & Data Quality Checks

Use WHERE to filter rows before grouping, and HAVING to filter aggregated groups after counting or summing:

-- 1. Summarize total completed spend per customer (filtering groups > 200)
SELECT c.customer_id,
       c.full_name,
       COUNT(o.order_id)   AS completed_orders,
       SUM(o.total_amount) AS total_spend
FROM customers c
INNER JOIN orders o ON c.customer_id = o.customer_id
WHERE o.order_status = 'COMPLETED'
GROUP BY c.customer_id, c.full_name
HAVING SUM(o.total_amount) > 200.00;

-- 2. QA Integrity Check: Detect duplicate email addresses in customers table
SELECT email, COUNT(*) AS duplicate_count
FROM customers
GROUP BY email
HAVING COUNT(*) > 1;

-- 3. QA Integrity Check: Detect negative or zero order totals
SELECT order_id, total_amount
FROM orders
WHERE total_amount <= 0;

6. Intermediate SQL: CTEs, Window Functions & Safe Transactions

Common Table Expressions (CTEs) make multi-step verification queries readable, while Window Functions (ROW_NUMBER()) let you inspect each customer's latest record without collapsing rows:

-- 1. CTE + Window Function: Fetch each customer's most recent order
WITH RankedOrders AS (
    SELECT order_id,
           customer_id,
           order_status,
           total_amount,
           order_date,
           ROW_NUMBER() OVER (
               PARTITION BY customer_id
               ORDER BY order_date DESC, order_id DESC
           ) AS row_num
    FROM orders
)
SELECT order_id, customer_id, order_status, total_amount, order_date
FROM RankedOrders
WHERE row_num = 1;

-- 2. Safe Test Data Updates: Always wrap manual test-DB edits in a transaction
BEGIN TRANSACTION;

UPDATE orders
SET order_status = 'COMPLETED'
WHERE order_id = 105;

-- Verify the exact row count before committing!
SELECT * FROM orders WHERE order_id = 105;

-- Run COMMIT; if accurate, or ROLLBACK; to undo immediately
ROLLBACK;
