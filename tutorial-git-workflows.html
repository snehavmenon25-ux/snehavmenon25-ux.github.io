1. Initial Setup & Essential Configuration

Before cloning or committing to any repository, configure your identity, default branch name, and line-ending behavior so your commits stay clean across Windows, macOS, and Linux CI agents:

# 1. Set your name and email (attached to every commit)
git config --global user.name "Your Name"
git config --global user.email "you@example.com"

# 2. Default to 'main' for newly initialized repositories
git config --global init.defaultBranch main

# 3. Prevent line-ending (CRLF vs LF) noise across Windows and Linux
# On Windows:
git config --global core.autocrlf true
# On macOS / Linux:
git config --global core.autocrlf input

# 4. Verify your active configuration
git config --list

2. How Git Tracks Changes (The 4 Areas)

Understanding where your files live avoids most beginner Git confusion:

  1. Working Directory: The actual files on your laptop that you edit in VS Code or Visual Studio.
  2. Staging Area (Index): The preview box (git add) where you select which changes belong in your next commit.
  3. Local Repository (.git): Your local commit history saved on disk via git commit.
  4. Remote Repository (GitHub / Azure Repos): The shared team server synced via git fetch, git pull, and git push.

3. Daily Feature-Branch Workflow (Step-by-Step)

In team environments, engineers typically avoid committing directly to main. Instead, follow this repeatable feature-branch loop for every new test suite or bug fix:

# 1. Switch to main and pull the latest team changes
git checkout main
git pull origin main

# 2. Create and switch to a descriptive feature branch
git checkout -b feature/checkout-api-tests

# 3. Check which files you modified or added
git status
git diff

# 4. Stage specific files and commit with a clear, imperative message
git add tests/test_checkout_api.py pages/checkout_page.py
git commit -m "Add negative promo-code API tests for checkout flow"

# 5. Push your branch to the remote repository and open a Pull Request
git push -u origin feature/checkout-api-tests

Pull Request Hygiene Tip: Keep PRs focused on one task (ideally under 300–400 changed lines), verify your .gitignore excludes .venv/, bin/, obj/, and test-results/, and confirm CI smoke checks pass before requesting review.

4. Branching Strategies Compared

  • GitHub Flow (Feature Branch + PR): One long-lived main branch; every feature or test suite lives on a short-lived branch merged via Pull Request after CI checks pass. Best for continuous deployment and Agile QA teams.
  • Trunk-Based Development: Engineers merge small, frequent commits into main daily (or via very short-lived branches lasting less than 24 hours), relying on feature flags and fast automated CI gates.
  • GitFlow (Release / Hotfix Branches): Uses separate develop, release/*, and hotfix/* branches. Useful when supporting multiple scheduled enterprise software versions simultaneously.

5. Resolving Merge Conflicts & Stashing Work

Temporarily Shelving Uncommitted Changes (git stash)

# Save unfinished edits so you can switch branches cleanly
git stash push -m "WIP: payment timeout test"

# Switch branches, inspect something, then return and restore your work
git checkout main
git checkout feature/checkout-api-tests
git stash pop

Syncing with main & Resolving Conflicts

# Bring latest main changes into your feature branch
git checkout feature/checkout-api-tests
git fetch origin
git merge origin/main

# If Git reports a CONFLICT in a file, open it and look for markers:
# <<<<<<< HEAD
#   your local branch code
# =======
#   incoming main branch code
# >>>>>>> origin/main

# Edit the file to keep the valid combined code, remove the <<<, ===, >>> markers, then:
git add path/to/resolved_file.py
git commit -m "Resolve merge conflict with main in checkout tests"

6. Safely Undoing Mistakes (Cheat Sheet)

  • Discard unsaved edits in a single file: git checkout -- path/to/file.py (or git restore path/to/file.py)
  • Unstage a file you accidentally ran git add on: git restore --staged path/to/file.py
  • Fix a typo in your most recent local commit message: git commit --amend -m "Corrected commit message" (use only before pushing to a shared branch)
  • Safely undo a commit already pushed to main: git revert <commit-hash> — creates a new inverse commit without rewriting shared history.
  • Inspect compact visual branch history: git log --oneline --graph --decorate -n 15
