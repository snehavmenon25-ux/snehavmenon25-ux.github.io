1. How CI/CD Fits Into Automated Quality Engineering

Running automation scripts manually on a local laptop catches defects too late. A Continuous Integration / Continuous Delivery (CI/CD) pipeline splits quality gates into two automated stages:

  • Build / CI Pipeline (On Every Pull Request or Commit): Restores dependencies, compiles the application or test project, runs fast headless smoke tests, and blocks merges if critical tests fail.
  • Release / CD Pipeline (On Staging / QA Deployment): Deploys the build artifact to a staging environment, injects environment-specific URLs and secrets, executes full UI/API regression suites, and publishes HTML/TRX/JUnit reports.

2. Part A — Jenkins Declarative Pipeline (Jenkinsfile)

Step 1: Recommended Jenkins Plugins

Before creating your pipeline job in Jenkins (Manage Jenkins → Plugins), confirm these standard plugins are installed:

  • Pipeline: Enables declarative Jenkinsfile workflows stored directly in Git.
  • Git / GitHub Integration: Triggers builds automatically via webhooks on push or pull request.
  • JUnit & HTML Publisher: Displays pass/fail trends and attaches Playwright HTML reports or screenshots to each build.
  • Credentials Binding: Injects passwords and API keys safely without hardcoding them in Git.

Step 2: Complete Jenkinsfile for Playwright (Python) & Selenium (.NET)

File: Jenkinsfile (Place in the root of your repository)

This declarative pipeline runs headless browser tests, archives failure traces/screenshots even when a test fails (post { always { ... } }), and publishes structured results.

pipeline {
    agent any

    environment {
        // Non-sensitive defaults; secrets come from Jenkins Credentials Store
        BASE_URL = 'https://demo.playwright.dev/todomvc/#/'
        CI       = 'true'
    }

    stages {
        stage('Checkout Code') {
            steps {
                checkout scm
            }
        }

        stage('Setup Python & Playwright') {
            steps {
                sh '''
                    python3 -m venv .venv
                    . .venv/bin/activate
                    pip install --upgrade pip
                    pip install pytest pytest-playwright pytest-html
                    playwright install chromium
                '''
            }
        }

        stage('Run Automated Smoke & Regression Tests') {
            steps {
                withCredentials([string(credentialsId: 'qa-test-token', variable: 'API_TOKEN')]) {
                    sh '''
                        . .venv/bin/activate
                        pytest --headed=false \
                               --junitxml=reports/junit-results.xml \
                               --html=reports/playwright-report.html \
                               --self-contained-html \
                               --tracing=retain-on-failure
                    '''
                }
            }
        }
    }

    post {
        always {
            // Publish JUnit XML so Jenkins tracks test pass/fail trends over time
            junit allowEmptyResults: true, testResults: 'reports/junit-results.xml'

            // Archive HTML reports and Playwright failure traces as downloadable build artifacts
            archiveArtifacts artifacts: 'reports/**, test-results/**', allowEmptyArchive: true
        }
    }
}

Step 3: Creating the Job in Jenkins

  1. Click New Item → enter QA-Regression-Pipeline → select Pipeline → click OK.
  2. Under Triggers, check GitHub hook trigger for GITScm polling (or schedule nightly runs with H 2 * * * under Build periodically).
  3. Under Pipeline → Definition, choose Pipeline script from SCM, select Git, paste your repository URL, and set Script Path to Jenkinsfile.
  4. Click Save and press Build Now to verify all three stages turn green.

3. Part B — Azure DevOps Build & Release YAML Pipeline

Modern Multi-Stage YAML vs. Classic Build & Release

In Azure DevOps, you can configure Classic UI Build/Release pipelines or combine both into a single version-controlled azure-pipelines.yml file with separate Build_And_Smoke and Deploy_And_Regression_Release stages.

Complete Multi-Stage azure-pipelines.yml (Selenium C# + NUnit/MSTest)

File: azure-pipelines.yml (Place in the root of your .NET repository)

Notice how Stage 1 compiles the .NET solution and publishes build artifacts, while Stage 2 (the Release gate) downloads those artifacts, runs headless Selenium tests against Staging, and uploads the Visual Studio .trx report into the Azure DevOps Tests tab.

trigger:
  branches:
    include:
      - main

pr:
  branches:
    include:
      - main

pool:
  vmImage: 'ubuntu-latest'

variables:
  buildConfiguration: 'Release'

stages:
  # =========================================================
  # STAGE 1: BUILD PIPELINE (Compile & Publish Test Artifacts)
  # =========================================================
  - stage: Build_Stage
    displayName: 'CI Build & Package Tests'
    jobs:
      - job: BuildJob
        displayName: 'Restore, Build & Publish'
        steps:
          - task: UseDotNet@2
            displayName: 'Install .NET 8 SDK'
            inputs:
              packageType: 'sdk'
              version: '8.0.x'

          - script: dotnet restore WebAutomation.Tests/WebAutomation.Tests.csproj
            displayName: 'Restore NuGet Packages'

          - script: dotnet build WebAutomation.Tests/WebAutomation.Tests.csproj --configuration $(buildConfiguration) --no-restore
            displayName: 'Build Test Project'

          - task: PublishBuildArtifacts@1
            displayName: 'Publish Compiled Test Binaries'
            inputs:
              PathtoPublish: 'WebAutomation.Tests/bin/$(buildConfiguration)'
              ArtifactName: 'qa-test-binaries'

  # =========================================================
  # STAGE 2: RELEASE PIPELINE (Staging QA Execution & Report)
  # =========================================================
  - stage: Release_QA_Stage
    displayName: 'Release Gate: Staging UI Regression'
    dependsOn: Build_Stage
    condition: succeeded()
    jobs:
      - deployment: RunStagingRegression
        displayName: 'Execute Selenium Suite on Staging'
        environment: 'QA-Staging'
        strategy:
          runOnce:
            deploy:
              steps:
                - checkout: self

                - task: UseDotNet@2
                  displayName: 'Install .NET 8 SDK'
                  inputs:
                    packageType: 'sdk'
                    version: '8.0.x'

                - script: |
                    dotnet test WebAutomation.Tests/WebAutomation.Tests.csproj \
                      --configuration $(buildConfiguration) \
                      --logger "trx;LogFileName=StagingResults.trx" \
                      --results-directory $(Agent.TempDirectory)/TestResults
                  displayName: 'Run Headless Selenium Tests'
                  env:
                    TEST_ENV_URL: 'https://the-internet.herokuapp.com/login'
                    # Map secret variable from Azure DevOps Library Variable Group
                    TEST_USER_PASSWORD: $(StagingTestPassword)

                - task: PublishTestResults@2
                  displayName: 'Publish TRX Results to Azure DevOps'
                  condition: always()
                  inputs:
                    testResultsFormat: 'VSTest'
                    testResultsFiles: '**/*.trx'
                    searchFolder: '$(Agent.TempDirectory)/TestResults'
                    failTaskOnFailedTests: true

Setting Up Secrets & Approval Gates in Azure DevOps

  1. Store Passwords Safely: Go to Pipelines → Library → + Variable group, add StagingTestPassword, and click the padlock icon to mark it as a secret.
  2. Add Pre-Deployment Approvals: Go to Pipelines → Environments → QA-Staging → Approvals and checks to require QA Lead sign-off before releasing to UAT or Production.
  3. Inspect Test Analytics: After a pipeline run completes, open the Tests tab on the summary page to inspect stack traces, duration trends, and flaky test history.

4. Common CI/CD Troubleshooting Checklist for QA Engineers

  • Tests pass locally but fail in CI with "element not clickable": Linux CI agents default to small viewport resolutions (such as 800×600). Explicitly pass --window-size=1920,1080 in ChromeOptions or viewport dimensions in Playwright.
  • Pipeline stops before publishing reports when a test fails: By default, a failed dotnet test or pytest step aborts subsequent steps. Always add condition: always() in Azure DevOps or post { always { ... } } in Jenkins on report-publishing tasks.
  • Browser version mismatch on self-hosted agents: Use Selenium 4's built-in Selenium Manager or run playwright install inside the pipeline so driver binaries always match the installed browser version.
